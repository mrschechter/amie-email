# Codex work brief: Amie composer v3 — edit operations, not regeneration (Ian, 2026-09-02 night)

Ian on the live editor: "the amie assistant is super slow and doesn't really work." Evidence: he asked "do you see how in the email header the word ready is on its own line, can we fix that?" — the message was sent twice, the assistant took ~20s, and replied "Updated. No fixes needed — CTA is above the fold, footer is present, block count (11)…" without changing anything. Root causes: (1) every chat turn re-plans the entire block document and re-assembles (large output ⇒ slow, regardless of Bedrock vs direct API); (2) the model never sees the rendered text, so layout requests are meaningless to it; (3) it falls back to a validation checklist reply when it has nothing to change; (4) Enter-to-send fires twice (keydown handler + form submit).

Stay on Bedrock (HIPAA-covered) with AMIE_COMPOSER_MODEL_ID / _FAST = us.anthropic.claude-sonnet-5. Rebuild the assistant loop as an EDITOR:

## 1. Edit-ops contract (packages/isomorphic-lib amieComposer types + packages/api amieComposerController + backend-lib amieBlocks/amieLiquid)
- New endpoint `POST /content/templates/compose/edit` taking { workspaceId, templateId, message, conversation, document: { subject, previewText, blocks, rawHtml? }, renderedText } and returning { reply, ops: EditOp[], warnings } where EditOp ∈ set_subject, set_preview_text, replace_text{blockId, find, replace}, set_block_props{blockId, props}, insert_block{afterBlockId, block}, remove_block{blockId}, move_block{blockId, afterBlockId}, set_style_token{name, value}, no_op{reason}. Ops are validated server-side (block ids exist, Liquid-safe via normalizeLiquid, styles from the allowed token set) and applied to produce the new document + assembled HTML; return both.
- The prompt gives the model: the block document (ids + text), the RENDERED TEXT with line breaks as the preview shows them (render the assembled HTML to text with a 600px-aware wrap heuristic per block — plain-text extraction is fine, plus the last 2 words of each heading flagged as "widow candidates"), the user-property catalog, and rules: prefer the smallest op set; for "word on its own line / orphan / widow" use replace_text inserting &nbsp; between the last two words or shorten the heading; NEVER answer with a checklist; if nothing should change, return no_op with a one-sentence reason and a suggestion.
- Route: edit requests → FAST model with max_tokens ≈ 1,200 (ops are small). Only explicit "write a new email / start over / draft" intents use the existing full-draft path. Quick actions (Shorten it, Add 15% offer, A/B variant, SMS version) become edit-op prompts too, except A/B and SMS which keep their existing flows.
- Streaming: stream the `reply` text first (so the user sees words within ~1s), then ops apply atomically when the JSON tail arrives; show "Applying 2 changes…" then "Done" in the chat; the preview re-renders once.
- Target: p50 under 4s for an edit turn. Log per-turn timing (model, tokens, ms) as today.
